We are encountering a race condition where accepted API edits to notes (e.g., via `PATCH` or `POST /write`) can result in missing vector embeddings for observations and relations. This happens because write routes eagerly schedule a vector sync (e.g., using `LocalEntityVectorSyncScheduler`) that races with the background file materialization job. The eager sync often runs first and embeds just the temporary body-only search projection. When materialization later finishes processing the actual observation and relation rows, no subsequent vector sync is scheduled to capture them. Furthermore, overlapping sync tasks for the same note can cause other consistency issues, such as publishing obsolete chunks or incorrectly clearing deferred markers.

To resolve this, we need to guarantee that an accepted write embeds its vectors exactly *once*, and only *after* the file is fully materialized and indexed.

Expected behavior and required changes:
1. Move vector sync ownership to the materialization pipeline. Modify `LocalNoteContentMaterializationProvider` to accept an optional `entity_vector_sync` async callback parameter. Update the factory function `get_note_content_materialization_provider` to pass this callback using the search service's vector sync capabilities.
2. Inside `LocalNoteContentMaterializationProvider`, after a file finishes materialization (e.g., at the end of `_materialize_write_now`), it should queue exactly one vector sync for that note on a new, separate internal task pool (e.g., `_vector_sync_pool`). Similar to the materialization pool, these vector tasks must be keyed/grouped by the note ID so that multiple syncs for the same note run sequentially, never concurrently.
3. The vector sync execution wrapper in the pool should also trigger a read cache invalidation for the note's project upon completion.
4. Update the `drain_pending_materializations` function to ensure it drains the materialization pool first, and then drains the new vector sync pool.
5. Stop eager vector sync scheduling in the API and service layers for note operations. Remove the request-time vector sync triggers from the planners/routes handling note creation, update, edit, and `POST /write`, since the materialization job now inherently handles it. 
6. For directory moves (e.g., `move_directory`), keep scheduling a vector sync per directory. Moved regular files (like images or PDFs) do not have note materializations but still require search-graph updates.
